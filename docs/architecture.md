# Архитектура сервиса анализа новостного фона компаний (.ru)

Документ покрывает часть 1 задания: обоснование стека, расчёт мощностей и план
реализации MVP с дальнейшим масштабированием до production-ready.

---

## 1. Назначение и контекст

Сервис собирает новости из домена `.ru`, привязывает их к компаниям и формирует
**новостной фон**: что писали о компании, насколько негативно/позитивно, какие
события сгруппированы вместе. Целевой потребитель — отдел экономической
безопасности / форензики, для которого первичен **ранний детект негатива**
(иски, банкротства, уголовные дела, аварии, отзывы лицензий).

Ключевые функциональные блоки:

1. **Сбор** — парсинг/RSS/API новостных источников `.ru`.
2. **Обработка** — извлечение атрибутов (компания, регион, отрасль), кластеризация,
   оценка тональности и ранжирование.
3. **Хранение и выдача** — БД + API + дашборд/алерты.

В этом репозитории реализован вычислительный центр блока 2 (модули кластеризации
и тональности) и API вокруг них. Сбор и хранение описаны как план.

## 2. Обоснование стека

Требования вакансии: **Python, FastAPI, Docker**. Ниже — почему этот стек
оптимален именно для задачи, а не только «потому что в требованиях».

| Слой | Выбор | Обоснование |
|------|-------|-------------|
| Язык | **Python 3.12** | Экосистема NLP/ML под русский язык (Natasha, pymorphy2, spaCy, RuBERT/HF, scikit-learn) — то, чего нет в других стеках в таком объёме. |
| API | **FastAPI + Uvicorn** | Асинхронность (важно для I/O-bound сбора), автодокументация OpenAPI/Swagger, валидация через Pydantic v2 (быстрая, на Rust-ядре), нативная работа с типами. |
| Схемы данных | **Pydantic v2** | Контракты вход/выход, строгая валидация, сериализация — снижает класс ошибок на границе сервиса. |
| Классическая ML/векторизация | **scikit-learn + NumPy** | TF-IDF и агломеративная кластеризация «из коробки», предсказуемы, не требуют GPU, легко объяснимы. |
| NLP (план, prod) | **Natasha / pymorphy2 / RuBERT (HuggingFace)** | Лемматизация и NER под русский; дообученный RuBERT для тональности. |
| Очередь задач | **Celery / RQ (Redis)**, далее **Kafka** | Развязка сбора и обработки, ретраи, горизонтальное масштабирование воркеров. |
| Хранилище | **PostgreSQL 16** (+ `pgvector`) | Транзакции, надёжность, полнотекстовый поиск (`tsvector`), хранение эмбеддингов для семантической кластеризации/поиска дублей. |
| Кэш/брокер | **Redis** | Кэш справочников, дедупликация, брокер очереди. |
| Контейнеризация | **Docker + docker-compose**, далее **Kubernetes** | Воспроизводимость окружения, простое масштабирование воркеров и API независимо. |
| Наблюдаемость | **Prometheus + Grafana + structured logs (loguru/structlog), Sentry** | SLA по задержке обработки, алерты на рост ошибок/лагов очереди. |

**Принцип проектирования MVP:** модули тональности и кластеризации в прототипе
сделаны на детерминированных, объяснимых алгоритмах (лексикон + TF-IDF), без
обучающих данных и GPU. Это сознательный выбор: на старте важнее прозрачность и
быстрый запуск, а тяжёлые ML-модели подключаются за тем же интерфейсом по мере
накопления размеченных данных (см. §5).

## 3. Расчёт мощностей

### 3.1 Базовая нагрузка — 100 новостей в сутки

- 100 новостей/сутки ≈ **0,0012 новости/с** — пиков фактически нет.
- Стоимость обработки одной новости в текущей реализации (CPU, без GPU):
  - извлечение атрибутов + стемминг: ~1–3 мс;
  - тональность (лексикон): ~1–2 мс;
  - кластеризация считается **батчем за сутки** (агломеративная, O(n²) по парам):
    для n=100 это 100²/2 = 5 000 сравнений векторов — единицы миллисекунд.
- Суточный батч из 100 новостей обрабатывается за **доли секунды**.

**Вывод:** для 100 новостей/сутки достаточно **одного контейнера**:
`0,5 vCPU / 512 МБ RAM`. Запас по нагрузке — тысячекратный. БД на этом объёме —
минимальный инстанс (`1 vCPU / 1 ГБ`, диск от 10 ГБ).

### 3.2 Профиль ресурсов и узкие места

| Этап | Тип нагрузки | Узкое место при росте |
|------|--------------|------------------------|
| Сбор новостей | I/O-bound (сеть) | Лимиты источников, сетевые таймауты → решается async + очередь |
| Извлечение атрибутов / тональность (лексикон) | CPU-bound, лёгкий | Линейно масштабируется числом воркеров |
| Тональность на трансформере (prod) | CPU/GPU-bound, тяжёлый | Инференс модели → батчинг + GPU/выделенный inference-сервис |
| Кластеризация O(n²) | CPU + память | Рост батча → переход на ANN-индекс (HNSW/`pgvector`) |

### 3.3 Масштабирование до больших нагрузок

Оценки для CPU-обработки (лексикон + TF-IDF), 1 воркер ≈ 300–500 новостей/с на
типовом ядре (доминирует векторизация и парсинг):

| Поток | В секунду | Что нужно |
|-------|-----------|-----------|
| 100 / сутки (MVP) | ~0,001/с | 1 контейнер `0,5 vCPU / 512 МБ` |
| 100 000 / сутки | ~1,2/с | 1–2 воркера + очередь + PostgreSQL `2 vCPU / 4 ГБ` |
| 1 000 000 / сутки | ~12/с | 3–4 воркера API/обработки, Redis, PostgreSQL `4 vCPU / 8–16 ГБ`, партиционирование таблиц по дате |
| 10 000 000 / сутки | ~120/с | Kafka, автоскейл воркеров (k8s HPA), `pgvector`/ANN для кластеризации, отдельный GPU-инференс тональности, шардирование/реплики БД |

**Главный нелинейный риск — кластеризация.** Агломеративная сложность O(n²) по
памяти и времени неприемлема на больших батчах. План:
1. кластеризовать не «всё против всего», а **в окне** (по дате/компании/отрасли) —
   разбиение пространства снижает n в каждом батче;
2. перейти на **эмбеддинги + ANN-индекс** (HNSW в `pgvector` или FAISS): новая
   новость ищет ближайшие за O(log n) и присоединяется к существующему кластеру
   (онлайн-кластеризация вместо пересчёта всего батча).

## 4. Архитектура (целевая)

```
            ┌──────────────┐      ┌─────────────┐
 источники  │  Collectors  │ ──▶  │   Queue     │  (Redis/Celery → Kafka)
   .ru ───▶ │ (RSS/parsers)│      │  (raw news) │
            └──────────────┘      └──────┬──────┘
                                         │
                              ┌──────────▼───────────┐
                              │   Processing workers  │
                              │  • extract attributes │
                              │  • sentiment          │
                              │  • clustering (online)│
                              └──────────┬───────────┘
                                         │
                    ┌────────────────────▼────────────────────┐
                    │           PostgreSQL (+ pgvector)        │
                    │   news, attributes, clusters, sentiment  │
                    └────────────────────┬────────────────────┘
                                         │
                        ┌────────────────▼────────────────┐
                        │   FastAPI (этот репозиторий)     │
                        │  /analyze /cluster /sentiment    │
                        └────────────────┬────────────────┘
                                         │
                              Dashboard / Alerts / BI
```

В прототипе реализован вычислительный центр (FastAPI + модули). Коллекторы,
очередь и БД — следующий шаг (§5).

## 5. План реализации MVP → production

### Этап 0. MVP-ядро (реализовано в этом репозитории)
- [x] Модуль извлечения атрибутов (компания/регион/отрасль): словарь + правила.
- [x] Модуль кластеризации: TF-IDF + агломеративная кластеризация с атрибутным бустом.
- [x] Модуль тональности: лексикон + правила (отрицания, усилители), ранжирование.
- [x] FastAPI: `/health`, `/sentiment`, `/cluster`, `/analyze`.
- [x] Docker / docker-compose, тесты (pytest), демо-скрипт и датасет.

### Этап 1. Сбор и хранение (MVP → рабочий пайплайн)
1. Коллекторы источников `.ru` (RSS + парсеры), нормализация и **дедупликация**
   (хэш текста / шинглы).
2. PostgreSQL-схема: `news`, `companies`, `news_attributes`, `clusters`, `sentiment`.
3. Очередь (Celery + Redis): `collect → process → persist`, идемпотентность и ретраи.
4. Планировщик периодического сбора (Celery beat / cron).

### Этап 2. Повышение качества обработки
1. Лемматизация (pymorphy2/Natasha) вместо упрощённого стеммера.
2. NER для компаний вне словаря (Natasha/spaCy), линковка к справочнику (ЕГРЮЛ/СПАРК).
3. Тональность: дообученный **RuBERT**-классификатор; лексикон остаётся как
   fallback и источник объяснимости (какие термы дали оценку).
4. Кластеризация на **эмбеддингах предложений** + `pgvector`/ANN, онлайн-режим.
5. Доменная разметка негатива (финансовые/юридические риски) — приоритезация алертов.

### Этап 3. Production-ready
1. **Наблюдаемость:** Prometheus/Grafana (лаг очереди, p95 задержки, доля ошибок),
   structured logs, Sentry, алерты.
2. **Надёжность:** healthchecks, graceful shutdown, DLQ для «битых» новостей,
   реплики БД, бэкапы, миграции (Alembic).
3. **Масштабирование:** Kubernetes + HPA (автоскейл воркеров по длине очереди),
   партиционирование таблицы новостей по дате, выделенный inference-сервис тональности.
4. **Безопасность/эксплуатация:** аутентификация API (API-ключи/JWT), rate limiting,
   CI/CD, секреты в Vault/secret manager.
5. **Качество:** офлайн-метрики (precision/recall детекта негатива, чистота кластеров —
   silhouette/ручная разметка), регрессионные наборы, A/B новых моделей.

### Целевые нефункциональные требования (prod)
- Задержка «новость появилась → обработана и доступна в API»: **< 5 минут** (p95).
- Доступность API: **99,5%**.
- Полнота детекта явного негатива (иск/банкротство/уголовное дело): **recall ≥ 0,9**
  на размеченном наборе.

## 6. Замечания по текущему прототипу

- Стеммер и словари — **упрощённые** (для запуска без тяжёлых зависимостей и моделей).
  На ряде слов возможны ошибки нормализации и пересечения отраслевых ключей
  (например, «утечка топлива» у металлурга может пометиться как «Нефтегаз») —
  это устраняется лемматизацией и NER на этапе 2.
- Кластеризация работает на **уровне событий** (похожие по тексту новости об одной
  компании), а не просто `GROUP BY company`: атрибут компании уже извлекается
  отдельно и доступен для фильтрации, а кластер группирует именно сюжет.
- Пороги (`CLUSTER_DISTANCE_THRESHOLD`, `ATTRIBUTE_BOOST`, `SENTIMENT_NEUTRAL_BAND`)
  вынесены в переменные окружения и подбираются на размеченных данных.
